==================================================
1. FUNDAMENTAL INVENTORY PRINCIPLE
==================================================

NEVER make:

inventory_items.quantity

the source of truth.

Inventory is EVENT / TRANSACTION based.

Stock must be derived from movements.

Conceptually:

Opening Stock
    +
Receipts
    +
Returns
    +
Transfers In
    +
Positive Adjustments
    -
Issues
    -
Transfers Out
    -
Damage / Write-Off
    -
Negative Adjustments
    =
Stock On Hand

Every inventory movement must create an immutable stock transaction.

Never implement stock changes as:

item.quantity += 10
item.quantity -= 5

without a corresponding transaction/ledger record.

This principle is mandatory.

==================================================
24. ISSUE VALIDATION
==================================================

Before posting an issue:

- item must exist
- store must exist
- item/store organization must match
- quantity > 0
- sufficient AVAILABLE stock
- selected lot must contain enough stock
- serialized item must have correct serial
- expired stock should normally be blocked
- quarantined stock must be blocked
- project must be active where relevant
- asset must be valid where relevant
- employee must be valid
- approval must exist if required
- transaction must not make available stock negative

Do not allow negative stock by default.

Create an explicit privileged override only if Cestos later requests it.

==================================================

Consumption during lookback / number of relevant days

Expected Days Remaining =
Available Stock / Average Daily Usage

Estimated Stockout Date =
Current Date + Expected Days Remaining

If consumption = 0:

do not divide by zero.

Return:

==================================================
75. CONCURRENCY CONTROL
==================================================

This is critical.

Two storekeepers must not be able to simultaneously issue the final
10 units of an item.

Use PostgreSQL transaction/locking strategy when posting stock movements.

Appropriate options may include:

SELECT ... FOR UPDATE

on relevant inventory balance rows.

Posting must be atomic.

Example:

Available stock = 10

Request A = 8
Request B = 5

Both must not succeed.

One should succeed and the other receive insufficient-stock error.

Write a concurrency test if practical.

==================================================
76. IDEMPOTENCY
==================================================

Prevent duplicate posting caused by:

double-click
network retry
API retry

Posting endpoints should be idempotent where practical.

A receipt must not accidentally post twice.

An issue must not deduct stock twice.

A transfer receipt must not add stock twice.

Use document status plus transaction integrity and, if appropriate,
idempotency keys.

==================================================
77. REVERSALS
==================================================

Posted transactions should not simply be deleted.

Implement reversal architecture.

A reversal should:

reference original transaction
create opposite ledger effect
preserve original transaction
record reason
record actor
record timestamp

Example:

Original:
ISSUE -50 L

Correction:
REVERSAL +50 L

Then create correct transaction if needed.

==================================================
101. CRITICAL INVARIANTS
==================================================

The implementation is NOT complete if any of these can happen:

- Stock changes without a ledger transaction.
- Posted transactions can simply be deleted.
- Posted transactions can be freely edited.
- A transfer can disappear between stores.
- Two concurrent issues can create accidental negative stock.
- Expired/quarantined stock can be issued normally.
- An employee can access another organization's stock.
- An adjustment can occur without a reason.
- Historical inventory cannot be reconstructed.
- Inventory balances disagree silently with ledger.
- Cost calculations use floating-point values.
- Transfers are counted as consumption.
- Reserved stock is treated as freely available.
- In-transit stock is treated as destination available stock.
- A retry can post the same issue twice.
- Serial numbers can be issued twice simultaneously.
